Lock Spark ​

Der Lock Spark legt eine Sperrebene über ein Forge-Element oder über ein gezieltes Unterelement. Während der Sperre werden alle Zeigerinteraktionen mit dem Element einschließlich seines gestalteten Rahmens blockiert. Er kann je nach Benutzer, Adminstatus, PIN, Code oder Bestätigung entsperrt werden.

TIP

Der Spark schützt die Bedienung in der Oberfläche. Er ersetzt keine serverseitige Home-Assistant-Berechtigung.

Grundnutzung ​

yaml
type: custom:uix-forge
forge:
  mold: card
  sparks:
    - type: lock
      locks:
        - pin: 1234
          admins: true
element:
  type: tile
  entity: light.living_room

Ziel mit for wählen ​

Ohne for wird das ganze Forge-Element gesperrt. Mit for kann ein bestimmtes Element gesperrt werden, zum Beispiel nur das Tile-Icon.

yaml
type: custom:uix-forge
forge:
  mold: card
  sparks:
    - type: lock
      for: hui-tile-card $ ha-tile-icon
      locks:
        - pin: 1234
          admins: true
element:
  type: tile
  entity: light.living_room

WARNING

In Entities-Karten lassen sich die inline dargestellten Zeilen nur als ganze Zeile sperren; tieferes Overlay-Targeting funktioniert dort nicht. for unterstützt ansonsten die UIX-DOM-Pfade einschließlich $ für Shadow Roots.

Nutze keine PINs für echte Sicherheitsgrenzen. UIX läuft im Browser und kann Bedienfehler vermeiden, aber keine Home-Assistant-Rechte erzwingen.

Badges als Ziel ​

Wenn eine Sperre auf hui-badge zielt, auch bei der üblichen Konfiguration mold: badge, wird die Sperrebene direkt an der gerenderten Badge-Oberfläche angebracht. Das Schloss erhält standardmäßig left: 24px ohne vertikalen Versatz.

Mit icon_position lässt sich die Position gezielt ändern. Ein expliziter Wert ersetzt den Badge-Standard vollständig. Gib deshalb auch left: 24px an, wenn du nur top oder bottom ergänzen und die übliche horizontale Position beibehalten möchtest.

yaml
type: custom:uix-forge
forge:
  mold: badge
  sparks:
    - type: lock
      icon_position:
        top: -10px
        left: 24px
      locks:
        - code: 1234
          admins: true
element:
  type: entity
  entity: sensor.backup_next_scheduled_automatic_backup

Matching-Logik ​

locks wird in der angegebenen Reihenfolge geprüft. Der erste passende aktive Eintrag bestimmt die Entsperrung. Ein passender Eintrag mit active: false ist nur der Rückfall, wenn kein passender aktiver Eintrag folgt. Er überstimmt daher keine später passende aktive Sperre. Ohne passenden Eintrag ist das Element bei permissive: true frei; andernfalls umgehen Administratoren die Sperre, während andere Nutzer dauerhaft blockiert bleiben.

KonfigurationWen sie trifft
users-Liste vorhandenNutzer, deren Name in der Liste steht. Mit admins: true zusätzlich Admins.
Keine users-ListeAlle Nicht-Admins, die nicht in except stehen.
Keine users-Liste und admins: trueAlle Nutzer, Admins und Nicht-Admins, sofern sie nicht in except stehen.

Aktionen bei Fehlversuchen ​

Entwicklungsstand ab 9.2.0-beta.1

Die früheren retry_event / failed_event werden durch retry_action / failed_action ersetzt. Dies beschreibt den Entwicklungszweig, keine Funktion der stabilen Basis 9.1.0.

Mit retry_action führst du nach jedem falschen Code eine normale Home-Assistant-Action aus. failed_action läuft zusätzlich beim Grenzwert max_retries. Die Aktionen können auch von Nicht-Administratoren verwendet werden; die Berechtigungen des aufgerufenen HA-Dienstes gelten weiterhin. Beim letzten Fehlversuch führt UIX zuerst retry_action, dann failed_action aus. Konfiguriere beide bewusst, wenn dadurch zwei Meldungen entstehen können.

yaml
locks:
  - code: 1234
    admins: true
    max_retries: 3
    failed_action:
      action: perform-action
      perform_action: persistent_notification.create
      data:
        title: UIX lock failed
        message: A user reached the maximum number of incorrect code entries.
